# 关联基质语料

## 这是什么

**一把尺子，不是一个数据集。** 200 条虚构的中文日常记忆（10 个词场 × 20 条）+ 40 条带
ground truth 的查询，用来回答 P4a 的三个问题：

1. 图 A 的边权（关联码的 Jaccard）能不能把**相关的**和**无关的**分开；
2. 神经元级 W（关联码矩阵的 Gram）在**多大规模**上还剩吸引域；
3. 关联码取多少位合适 —— `memcore/sdr.py` 里那个 `ASSOC_K = 64` 的出处**不可达**
   （见 `sdr.py:163-174` 的 docstring），所以改由这里的曲线回答。

它是 `benchmarks/gold/` 之外的**第二份语料**，理由有两条：

- 金标准集的 `memories.jsonl` 只有 `{id, content}`，**没有簇标签**；「同簇 / 异簇」是
  `neighbor_auc` 的分母，没有它这个数无从定义。
- 金标准集是为**召回**造的，里面全是「每五分钟 / 每十分钟 / 每十五分钟」这种近义改写
  （硬负例）。拿它给「图」当尺子会像 README 说的**拿错尺子**——而且近义改写恰好会让关联
  图的 top-m 邻居全是自己的近重复项。

语料**全部虚构**，不含任何关于作者本人、本人机器、或本项目其它仓库的痕迹；这条由
`tests/test_substrate_gate.py` 用 `bench.PERSONAL_DENYLIST` 机械执行。

## 文件

| 文件 | 是什么 |
|---|---|
| `memories.jsonl` | 200 条记忆，一行一条，带 `cluster` |
| `queries.jsonl` | 40 条查询 + ground truth，一行一条，带 `cluster` |
| `freeze.json` | 两份 JSONL 的 `sha256(原始字节)`、条数、簇普查、schema 版本 |
| `baseline.json` | 默认档的**实测**基线与容差（先跑后填，见下） |
| `CORPUS.md` | 本文件 |

### `memories.jsonl` 字段

`id`（`s-0001` 形式）、`cluster`、`content`。

### `queries.jsonl` 字段

`id`（`q-01` 形式）、`cluster`、`query`、`expect`（同簇的另外三条；词法基线够不到的那部分）。

**`cluster` 对记忆和查询都出现**，而两者必须同源：`substrate_structural_violations` 会报出
「`expect` 为空」与「`expect` 跨簇」两类，它们和「边指向不存在的节点」一样是**结构不变量**，
退出码 3 —— 那是 bug，不是标定问题。

## 十个簇：**词场**，不是主题

`network` / `water` / `kitchen` / `commute` / `invoice` / `project` / `medication` /
`plant` / `photo` / `course`，每簇 20 条。

**这个定义是本语料最容易读错的地方，所以写在这里。** 簇内共享**有区分度的词汇**，而不是
共享话题。举例，`water` 簇的高频词是 水管 / 接口 / 渗水 / 生料带 / 水压 / 地漏 / 保温；
`network` 簇是 路由器 / 宽带 / 光猫 / 网线 / 信号 / 网速。

**为什么要这样定**：`encode_assoc` 是 `encode_lexical` 的**纯子集**（`idx` 照搬、权重照搬），
它只承载**词面**信息，看不见主题。第一版语料按**主题**分簇（`home` 簇里 20 条讲 20 件不同
的家居小事，彼此几乎不共享词汇），结果是 `neighbor_auc` 在 `k=32/64/128/256`、`hash/weight`
**每一档都停在 0.50 ± 0.03** —— 参数怎么改都不动。那不是参数问题，是**尺子拿错了**：
「同簇」这个标签对词法码来说是噪声，AUC 必然 0.5。

改成词场之后同一套代码、同一套参数，默认档 `neighbor_auc` 从 0.5054 涨到 **0.7083**。

**这不是把基准调绿。** 被测的对象是那个 k=64 的哈希子采样，它完全可能把这个信号毁掉
——`hash` 档的图 A 确实保住了相似度，但它的 W 是死的（`completion_top1` 0.0250，见下）。
语料只负责让「相关」这件事**在这个编码器的表达能力之内**，剩下的好坏由量具说。

### 本语料测不了什么

**它测不了「语义相关但用词不同」。** 那是语义通道的事，而 P4a 里语义通道**不存在**
（`sem_sdr` 这一版不落、`projection.py` 没写）。所以本语料的每一个数都是**词法量纲**上的数，
不能读成「基质懂了意思」。

## 怎么跑

```bash
uv run python tools/bench_substrate.py                       # 默认档（= 门槛绑的那一档）
uv run python tools/bench_substrate.py --check               # 与基线比，跌破容差即退出码 1
uv run python tools/bench_substrate.py --k 32,64,128,256     # 关联码取多少位
uv run python tools/bench_substrate.py --scale 200,2000,20000  # 容量悬崖在哪
uv run python tools/bench_substrate.py --assoc weight        # 换一条子采样规则
uv run python tools/bench_substrate.py --drop 0.5 --probes 200
uv run python tools/bench_substrate.py --json                # 额外一份机器可读报告
```

退出码：**0** = 达标（或只是报告）、**1** = 跌破基线容差（不是程序出错）、**2** = 用法或
环境不对、**3** = 结构不变量被违反（**那是 bug**）。

**门槛只绑默认档**（`assoc=hash`、`k=ASSOC_K`、`scale=` 语料条数 = 200）。
`--check` / `--freeze` 遇到 `--assoc weight` 直接退 2：扫描出来的那几行是用来**裁决参数
该取多少**的，冻住其中一个等于把一个待决问题伪装成一个已决问题。

**`graph_hit@*` / `mrr` 刻意不进门槛。** 它回答的是「第三通道该不该上」，而那还没有裁决
——P4b 的事。冻住一个还没裁决的数，会让 P4b 从「够不够好」变成「不许变坏」。

## 冻结纪律：四道锁

与 `benchmarks/gold/CORPUS.md` 同一套，缺一不可：

1. **语料指纹**。`freeze.json` 存两份 JSONL 的 `sha256(原始字节)` 与条数，
   `tests/test_substrate_gate.py` 断言相等，失败消息直接写出该做什么。
2. **`.gitattributes` 显式列 `*.jsonl text eol=lf`**。指纹失效比没有指纹更糟——守卫看起来
   还在。
3. **基线文件**。`baseline.json` 存受测配置全量、指标点估计、容差、语料指纹。判定 =
   `live >= baseline - tolerance`（两项都是越大越好，`GATED` 里写死）。
4. **防空转的反向断言**。基线必须自身像一份真实测量（`neighbor_auc >= 0.5`、
   `completion_top1 <= 0.995`），`--freeze` 生成时**强制重算、不接受手工输入**。没有这两条，
   「把基线写成全 0 就永远绿」是两步就能走到的状态，而且看起来完全正常。

**"先跑后填"的顺序**：实现 harness → 本地跑一次 `--json` → 把实测数**照抄**进
`baseline.json`（`--freeze` 生成）→ 此后 `--check` 才有意义。缺基线时 `--check` 是
`SystemExit`，**不是"没基线就跳过"**。

### 第 4 道锁的触达条件（验红记录，别误读成守卫坏了）

设计这道锁时的假设是「探针不扰动（`--drop 0`）→ 补全恒为 1 → 冻结出来的数什么都没量」。
**实测把这个假设推翻了一半**，记在这里：

```
  --drop 0 --freeze（默认档 hash）→ completion_top1 = 0.0200，退出码 0，**不触发**
  正交码（50 条互不相交的 64 位码）+ drop=0 → completion_top1 = 1.0000
      sanity_problems → ['completion_top1 = 1.0 > 0.995']   ← **触发**
```

也就是说，**hash 档的 W 塌到"连不扰动的探针都找不回自己"**（drop 0 与 drop 0.5 给出的
数几乎一样，0.0200 vs 0.0250）。这既是那条锁没在默认档触发的原因，也是「hash 的 W 是
死的」最强的一句陈述 —— 比 `completion_top1 = 0.0250` 本身说得更狠。

**这条锁不是空转的**：它拦的是"编码器改成近似正交之后，有人把 `--drop 0` 下恒为 1 的数
冻成基线"。上面第二行就是那一刻。要用它，先得有一个近似正交的编码器 —— 而那正是
`--assoc weight` 在做的事（见上一节），只是 `--check`/`--freeze` 按定义拒绝 `weight` 档。

**改语料时要动的三处**（同一次提交）：两份 JSONL → `freeze.json` → 重跑 `--freeze` 更新
`baseline.json`。

## 默认档的四个数（进门槛的两个标了 ←）

配置：`k=64 assoc=hash scale=200 drop=0.50 probes=200 top_m=8 min_weight=0.10`

```
  节点 200   有向边 1600   无向边 745（同簇 485 / 异簇 260）   孤点 18
  neighbor_auc          0.7083   ← 进门槛（0.5 = 瞎猜）
  neighbor_precision@m  0.6510
  completion_top1       0.0250   ← 进门槛
  completion_top5       0.1900
  confusion_rate        0.9750   （top-1 是别的记忆；P4c 的 sleep_confusion 就是这个口径）

  通道           hit@1     hit@8       mrr
  词法          0.8500    1.0000    0.9021
  图            0.8250    1.0000    0.8883
```

**第三通道那一行必须原样报出来，因为它现在没带来任何东西。** 图的 `hit@1` 0.8250 **低于**
词法基线的 0.8500，`mrr` 0.8883 也低于 0.9021。也就是说：在这套语料上，沿 A 扩散一步
**轻微地拖后腿**。这是 P4a 的合法结论之一，也正是「与词法基线并排报」要防的那件事——
不并排，这 0.8250 看起来像是"有个通道在工作"。

## 关联码取多少位：`--k` 曲线

```
  k=32  scale=200   AUC 0.6719  边准 0.5061  top1 0.0300  top5 0.2100  图mrr 0.8850
  k=64  scale=200   AUC 0.7083  边准 0.6510  top1 0.0250  top5 0.1900  图mrr 0.8883
  k=128 scale=200   AUC 0.6783  边准 0.7251  top1 0.0250  top5 0.1300  图mrr 0.8863
  k=256 scale=200   AUC 0.7324  边准 0.7630  top1 0.0300  top5 0.1200  图mrr 0.8863
  k=573 scale=200   AUC 0.7205  边准 0.8207  top1 0.0250  top5 0.0750  图mrr 0.8883
  k=1024 scale=200  AUC 0.7205  边准 0.8207  top1 0.0250  top5 0.0750  图mrr 0.8883
```

`k=573` 是 `LEXICAL_K`：关联码取满 = **词法码本身**，所以那一行是「A 建在词法码上」的
**上界**。`k=1024` 与它逐位相同（超过活跃位数就被截断），这是一条免费的实现自检。

读出来的三件事：

* **64 位子采样对 A 的排序质量几乎不花钱**：AUC 0.7205 → 0.7083（−0.012，在容差 0.02 之内）。
* **但对 `precision@m` 花得很多**：0.8207 → 0.6510（−0.17）。每节点的 8 个邻居里，靠哈希
  选出来的那批混进了更多异簇条目。P4b 的可视化如果画的是 top-m 邻域，这个数直接决定画面
  有多脏。
* **`completion_top1` 在**所有** k 上都是 0.0250–0.0300，包括 k=573。** 这一点推翻了
  「W 死是因为位太少」这个直觉——见下一节。

## 两条子采样规则，坐在分叉的两端

`--assoc` 有两条规则，都是 `encode_assoc(lex)` 的纯函数：

| | `hash`（默认） | `weight` |
|---|---|---|
| 选位 | `blake2b(index)` 摘要最小的 k 个，与权重无关 | 归一化词频最高的 k 个 |
| 200 条码的**并集位** | **552** / 4096 | **3224** / 4096 |
| 最高频位被多少条选中 | **125** / 200 | **61** / 200 |
| 两两 Jaccard 均值 | **0.0988**（≈ 词法码本身的 0.1053） | **0.0191**（≪ 词法码） |
| 无向边 / 孤点 | 745 / 18 | 243 / **105** |
| `neighbor_auc` | **0.7083** ✅ | 0.5287 ❌ |
| `neighbor_precision@m` | 0.6510 | 0.7078 |
| `completion_top1` | **0.0250** ❌ | **0.8700** ✅ |
| `confusion_rate` | 0.9750 | 0.1300 |

**这不是"哪个更好"，这是两个不同的东西**，而且解释就是那两行并集位：

* **`hash` 保相似**：码挤在一个 552 维的子空间里，词法结构被保住了（两两 Jaccard 与词法码
  几乎同值），所以 A 能分开同簇异簇。代价是 200 条码共享一个巨大的**公共分量**
  （最高频位 125/200 都选中），`W = AᵀA` 被这个分量淹没 —— 补全时能量被公共位主导，
  top-1 落在谁头上近乎随机（`confusion_rate` 0.9750）。
* **`weight` 近似正交**：码散在 3224 维里，两两 Jaccard 0.0191 已经**低于**词法码的 0.1053
  —— 它把词法相似度**扔掉了**，所以 A 分不开簇（AUC 0.5287 ≈ 瞎猜，孤点 105 个）。但正因为
  码之间近乎正交，W 是个干净的联想记忆：补全 0.8700。

**这就是计划书 §九 登记的那条分叉**（「关联码该保相似还是保正交」），量具把它变成了两个数。
而且**没人被迫二选一**：两条规则都是 `encode_assoc(lex)` 的纯函数，A 用一份码、W 用另一份
是完全可行的 —— 那是 P4b 的决定，本版只把它量出来。

## W 的容量悬崖：`--scale` 曲线

`--scale` 用**确定性合成语料**把 n 拉开：第 i 条 = 同簇两条句子的拼接，id `s-{i:04d}`，
无随机数、跨规模可比。默认档（`hash`）：

```
  k=64 scale=2000    AUC 0.9996  边准 0.9999  top1 0.0000  top5 0.0450  图mrr 0.3500
  k=64 scale=20000   AUC 1.0000  边准 1.0000  top1 0.0000  top5 0.0100  图mrr 0.3500
```

`weight` 档：

```
  k=64 scale=200      AUC 0.5287  边准 0.7078  top1 0.8700  top5 0.9700  图mrr 0.8896
  k=64 scale=500      AUC 0.8323  边准 0.9397  top1 0.2250  top5 0.6350  图mrr 0.5528
  k=64 scale=1000     AUC   n/a   边准 1.0000  top1 0.0900  top5 0.3000  图mrr 0.4494
  k=64 scale=2000     AUC   n/a   边准 1.0000  top1 0.0300  top5 0.1650  图mrr 0.3525
```

**读这一节之前先读这三条免责声明，否则整节都是骗人的：**

1. **`AUC 0.9996` 是合成语料的假象，不是"图变好了"。** 合成条目是**同簇两条句子的拼接**，
   于是同簇对里有大量近乎重复的句子，`min_weight=0.10` 之上只剩它们，异簇边**一条都不剩**
   —— 这就是 `scale >= 1000` 那两行 `AUC n/a` 的原因（分母为 0）。**不要把这几行读成容量
   变好或变差。**
2. **用副本而不是拼接会让最近邻永远是自己的影子**，AUC 虚高得更离谱，量到的就不是容量而是
   语料的重复度。拼接是这两种坏选择里较好的那个，但它仍然**不是两万条真实记忆**。
3. **`graph_mrr` 从 0.8896 掉到 0.3500 是同一个假象的另一面**：图里全是近重复对，扩散一步
   就把排名搅了。

**真正能读的是 `completion_top1` 那一列**（它只依赖 W，与簇标签无关）：

| n | 200 | 500 | 1000 | 2000 |
|---|---|---|---|---|
| `completion_top1`（weight） | 0.8700 | 0.2250 | 0.0900 | 0.0300 |

按 50% 丢位的探针，n=500 时补全正确率已经掉到 0.225，n=1000 时 0.09 —— 基本等于瞎猜
（随机基线 1/n = 0.001，但码之间的相关性把它抬到了 0.09）。

**这与计划书 §三 的负面预期在形状上一致**：经典 Hopfield 容量 ≈ `0.138·N`，N=4096 → 约
**570 条**，而本仓的关联码**相互相关**（相似文本共享位），相关模式只会把容量压得更低。
量出来的悬崖位置（n≈500 就开始塌）比 570 还早一点，方向对得上。

**结论（这是 P4a 存在的理由）**：全局 Hebbian W 在 5 万条的真实规模上**一步补全大概率不
可靠**。P4c 的吸引子回放要建在别的东西上（分簇、局部 W、或迭代去噪），而不是直接
「`complete(probe)` 取 top-1」。这个数先量出来，P4c 才不用在写完之后才发现。

## 分簇 + 局部 W：P4c 落地之后，那条曲线被推平了吗

**没有被推平。** P4c 取了上面三个备选里的第一条（分簇 + 每簇建自己的局部 W），下面是它
落地之后的实测：

```bash
uv run python tools/bench_consolidation.py            # 四档并排
uv run python tools/bench_consolidation.py --json     # 机器可读
```

四列问的是同一句话：50% 丢位的探针经**一步补全**之后，top-1 是不是它自己。前两列是同一
个**全局** W 换两条关联码（`hash` 是图 A 的那一档、`weight` 是 W 原来的那一档），后两列把
W 换成「只装它自己那一簇的成员」，分别用 `weight` 与**簇内文档频率的 `idf` 档**。后两列
就是 `RunReport.recognition_rate`，与 `tools/sleep_once.py` 在真实库上报的是**同一个数**。

```
    规模  全局W(hash)  全局W(weight)  分簇W(weight)  分簇W(idf)  簇数  最大簇    回放  认错J中位  认错J≥0.9
     200       0.0250         0.8700         0.9000      0.9950     7     105     200     0.0407      0.0%
     500       0.0050         0.2250         0.4400      0.5840    93      13     500     0.7778     30.3%
    1000       0.0000         0.0900         0.1370      0.3130   100      10    1000     0.8286     49.9%
    2000       0.0000         0.0300         0.1020      0.1960   190      20    2000     1.0000     95.5%
```

**`idf` 档在每一档都比 `weight` 高，而且 n=200 上已经接近满分。** 它是 2026-10-18
换上的默认档：把簇内文档频率当作 ALIF 的稳态适应变量，压掉跨条目公共位
（`memcore/sdr.py::encode_assoc_idf`）。真实库上也有一组直接读数：166 条记忆、2 个簇
（163 + 3），`weight` 0.6988 → `idf` **0.8976**；`sleep_once --dry-run` 的口径是 164 条
真回放、2 条 pinned 跳过，辨认率 **0.9085**。

**n=200 那一档（语料全量）是唯一一个能直接读的档。** 分簇把辨认率从 0.8700 抬到
**0.9000**（weight）/ **0.9950**（idf），而 idf 认错的那 1 条 J 中位只有 **0.0407**。
这一档里所有条目都是手写的原句（没有合成件），所以它量的是分簇与选位本身。

**n≥500 那三档要换一种读法，否则整节都是骗人的。** `idf` 档确实比 `weight` 高
（1.3–2.3 倍），但它**仍然随规模往下掉**，而掉的原因不在分簇：认错 J 的中位从 0.0407
一路涨到 1.0000，认错里 J≥0.9 的占比从 0% 涨到 **95.5%**——**top-1 认错的那一条与被回放
的那一条本来就几乎一模一样**。这正是上一节第 2 条免责声明说的那件事：`--scale` 造出来的
条目是**同簇两条句子的拼接**，于是簇内（以及原始条目与它们的拼接之间）互为近重复，丢了
一半位的探针根本分不出是哪一条。**这时辨认率量的是语料的重复度，不是 W 的容量。**

于是这份语料**分不开下面两件事**：

* 分簇把"容量"这个约束解掉了多少；
* 放大出来的近重复把辨认率压掉了多少。

要分开它们得有一份"同簇但不重复"的放大语料——**这一版没有造**（造了就是新语料，要另走
一遍冻结纪律）。所以这里只登记已经量到的那几条：

* **在真语料上（n=200）分簇是正的**：weight 0.9000 > 0.8700、idf 0.9950 > 0.9000，
  且 idf 的串扰距离小（J 中位 0.0407）；真实 166 条库上 idf 0.8976 > weight 0.6988。
* **在合成语料上（n≥500）分簇仍然比全局高，但曲线没有变平**，而那条下降趋势与"簇内近
  重复"同步——**没有证据说分簇在真实规模上够用，也没有证据说它不够用。**
* **簇规模不是被上限截的**：n=200 上图给出 7 个簇、最大 105（LPA 把十个词场并掉了一部分），
  n≥500 上中位是 6/10/10。`MAX_CLUSTER=200` 在这四档里**一次都没顶到**——分出来多大是图
  结构决定的。这也回答了"LPA 在真实规模的图上会给出什么"这个问题的一半：**它会并簇，而
  并出来的簇仍然远小于上限**。

**这一节不进门槛，理由同上**：本仓只有**默认路径**进门槛，而巩固**没有默认路径**——它不
参与召回，没有"用户实际走到的那条路"可言。所以 `tools/bench_consolidation.py` 只报告：
退出码只有 **0**（报告完了）与 **2**（用法或环境不对），**没有 1**，也没有 3。本文件与
`baseline.json` 一个字节都没被它动过。

**它自己会发现自己量错了。** 第一列与 `baseline.json` 里冻结的 `completion_top1` 按定义
是**同一个测量**（同一份语料、同一批探针、同一个算子、同一档图参数），所以脚本每次都拿
两者对表，对不上就在 stderr 上警告。这条守卫验过一次红：容差若借基线文件里那个 0.05，
它就哑了——`--drop 0.3` 让第一列从 0.0250 掉到 0.0200，差 0.003 < 0.05，照样不响。所以它
用的是自己的 1e-6（同一个测量差一点点就是口径变了，而"口径变了"在两张表里看起来都完全
正常）。

真实库上那一轮由 `tools/sleep_once.py` 输出，辨认率是同一个数；区别只是那边**没有对照
列**——在真实库上跑一遍全局 W 是没有意义的，这一节量出来的悬崖就是理由。

## 已知的局限

* **簇是词面关系，不是语义关系。** 见上面「本语料测不了什么」。所有数字都是词法量纲的。
* **n = 200（每簇 20）的统计噪声。** `neighbor_auc` 的分母是同簇对数 × 异簇对数
  （1900 × 18100），点估计稳；但 `graph_hit@*` 只有 40 条查询，容差 0.05 在 n=40 上约合
  2 条——所以它**不进门槛**。
* **`--scale` 上的数是合成语料上的数**，不是真实记忆上的数（见上）。
* **`completion_top1` 默认档是 0.0250，也就是"死的"。** 把它冻进基线，门槛的语义是
  **不许更差**，而不是"这个数有意义"。P4b 若把默认改成 `weight`，这条基线必然要重冻
  —— 那正是基线该有的行为。
* **语料只在 sdist 里，不在 wheel 里**（与金标准集同）。P6a 冻结的是 exe、产物不带
  `benchmarks/`，安装态那条仍然开着。
* **本版不做**：语义通道语料、共现边语料（要真实使用历史）、跨会话语料。
