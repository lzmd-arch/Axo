## 关联基质量具：图 A 与 W

**P4a 交付的是一个数，不是一次行为变更。** 这一版建出两样东西——关联图 A
（边 = 关联码的 Jaccard，每节点留 top-m 邻居）与神经元级基质 W（``AᵀA`` 的隐含表示，
不物化那张 4096² 的稠密矩阵）——但**没有任何东西把它们接进召回**：
`RecallConfig.graph_weight` 保持 0、`ChannelScores.graph` 保持恒 0、`recall.py` 一个字
没改。理由是 [bench.md](bench.md) 的「金标准集与门槛」里记着的那次实测否定结果（加语义通道让 AUC 涨了而 hit@8 跌了，
因为 `min_score` 是按词法量纲标定的）：**换通道组合要重标阈值，而那要真实库上的数据。**
所以 P4a 只做一件事：把"这套基质到底值不值得用"量出来。

量具在 `benchmarks/substrate/`（200 条虚构记忆，10 个**词场** × 20 条 + 40 条查询），
四项指标的口径写在 `axo.bench.substrate` 里，`tools/bench_substrate.py` 只报告：

```bash
uv run python tools/bench_substrate.py                        # 默认档，报四个数
uv run python tools/bench_substrate.py --k 32,64,128,256      # 关联码取多少位
uv run python tools/bench_substrate.py --scale 200,2000,20000 # W 的容量悬崖在哪
uv run python tools/bench_substrate.py --assoc weight         # 换一条选位规则
uv run python tools/bench_substrate.py --check                # 与基线比（CI 与 pre-commit 用这条）
```

**进门槛的只有两个数**：`neighbor_auc`（同簇边的权重高于异簇边的概率）与
`completion_top1`（确定性地丢掉一半活跃位之后还认得自己的比例）。它们是基质的**性质**，
全部输入是 blake2b 与 numpy——无随机数、无模型、无 GPU、无网络，所以能在 CI 里跑。
`graph_hit@*` / `mrr` **只报告、不进门槛**：它衡量的是"第三通道该不该上"这个问题，而
P4b 扫完一档之后答案是"默认不上"（见下节）。**答案出来了，门槛照旧不进**——那条记录的
是一条**路径**（换通道组合要重标 `min_score`），不是"够不够好"，冻住它会把将来的标定
变成"不许变坏"。

**实测出来的三件事**（完整留档在 `benchmarks/substrate/CORPUS.md`）：

1. **A 与 W 坐在分叉的两端。** 关联码的选位规则是 `encode_assoc` 的一个参数，两种取法
   各废一半：

   | 选位规则 | 200 条码的并集位 | 两两 Jaccard 均值 | `neighbor_auc` | `completion_top1` |
   |---|---|---|---|---|
   | `hash`（默认，摘要最小） | 552 / 4096 | 0.0988 | **0.7083** ✅ | 0.0250 ❌ |
   | `weight`（权重最高） | 3224 / 4096 | 0.0191 | 0.5287 ❌ | **0.8700** ✅ |

   `hash` 保相似（码挤在 552 维里，词法结构还在 → A 好；但公共分量淹没了 W → 补全死）；
   `weight` 近似正交（码散在 3224 维里 → A 塌；但 W 干净 → 补全活）。**两条规则都是
   纯函数**，所以"A 用一份码、W 用另一份"完全可行。**P4b 只用到 A**，所以这一半自然定了
   （A 用默认的 `hash` 档）；**W 那一半由 P4c 接手，用的正是 `weight` 档**——上面那两句
   在这里原样兑现，见下面「睡眠巩固（P4c）」。一份图、两份码，互不干扰。
2. **W 有容量悬崖，而且它来得比理论还早。** weight 档上 `completion_top1` 随规模的实测：
   n=200 → 0.8700、n=500 → 0.2250、n=1000 → 0.0900、n=2000 → 0.0300。与"经典 Hopfield
   容量 ≈ 0.138·N ≈ 570"的形状一致，拐点还更靠前（本仓的关联码互相相关，相关模式正是
   把吸引子容量压得更低的东西）。**结论：5 万条规模上全局 Hebbian W 的一步补全大概率
   不可靠**，P4c 的吸引子回放要建在别的东西上。这正是 P4a 存在的理由。
3. **第三通道现在没带来东西。** 图上的扩散 `hit@1` 0.8250 **低于**词法基线 0.8500，
   `mrr` 0.8883 也低于 0.9021——沿 A 扩散一步轻微拖后腿。这是 P4a 的合法结论，也正是
   "与词法基线并排报"要防的事（把两个数分开报，"图没带来什么"就会被含糊过去）。

> **两条必须连着报的注意事项。** 其一，`--scale` 放大语料用的是**合成**条目（同簇两条
> 句子拼接），n=20000 上那些数不是"两万条真实记忆"上的数；`--scale` 的分列标题里写着
> 这件事。其二，语料的第一版按**主题**分簇，`neighbor_auc` 在每一档都停在 0.50——参数
> 怎么调都不动。根因不是参数：簇是主题关系，而 `encode_assoc` 只承载**词面**信息。改成
> **词场**簇之后，同一套代码同一套参数：AUC 0.5054 → 0.7083、precision@m 0.2213 →
> 0.6510。**这不是把基准调绿**——被测对象仍是那个 64 位哈希子采样，它确实能把词面信号
> 毁掉（`k=573` 时 AUC 0.7205 / precision@m 0.8207，那是"A 建在词法码上"的上界）。

## 联想通道与邻居面板（P4b）

**P4b 的形状由 P4a 量出来的那个负数决定。** 既然"沿图扩散一步"量出来是拖后腿的，P4b 交付的
就不是"联想通道上线了"，而是三件各自站得住的事：通道**接上了**（可以打开）、打开要付
什么代价**已经量在纸上**、图本身**能看了**。

**通道：接上了，默认关。** `RecallConfig.graph_weight` 的默认值**仍然是 0.0**，所以
出厂行为逐位不变——`graph_weight=0` 时扩散**根本不算**（短路，不是"算了不用"），
`_scan` 的权重 dict 里连 `graph` 这个键都不加。这条是硬约束，有一条测试拿"同一份 config、
一次 `graph=<真图>` 一次 `graph=None`"比对整份账本。

设置页「记忆」里有一个「启用联想通道」勾选框，旁边**先写代价再写好处**：`min_score`
（0.10）是按词法量纲标定的，多一条通道会让它不再对应原来的严格程度。要打开的人应该先去
看 `benchmarks/gold/CORPUS.md` 里「联想腿」那一页——那里有一档扫描，四项指标没有一项变好，
AUC 从 0.9093 掉到 0.8450，`hit@1` 四列全平（联想只抬中后段，从不改榜首）。**为什么大概率
是负的，写在实现里**：图的边来自 `assoc_sdr`，而它是从 `lex_sdr` 派生出来的纯哈希子采样，
所以"联想找到的邻居"与"词法已经找到的东西"同源——加的是同一份证据的第二遍。

`_GRAPH_CHANNEL_WEIGHT = 0.25` 是**未标定的初值**，取的是扫描表里那一档（MRR −0.0037、
AUC −0.0172，比 w=1.00 的 −0.0643 轻得多）。真实库上要取多少，得等将来那一轮**标定**
（它还没排进 [development.md](development.md) 的阶段表）——在那之前**注释里写着不要往上调**。

**大库上的种子与候选。** 50k 语料上，旧实现为了取每个图节点的 Jaccard 会
`iter_items()` 解码全库 SDR（实测 2.3–3.1 s）；现在走 `LexicalIndex.scores()`，
0.08 s，宽度不同的节点仍然不给种子。扩散后正分节点在 50k 放大语料上是 50,000 条，
直接并进候选会超过 20,000 上限而回退全量扫描；`_GRAPH_CANDIDATE_LIMIT = 5000`
只把扩散分最高的 5,000 条并进候选集，不改变被扫条目的打分。50k 端到端（链式
stub 图）召回 552 ms、扫描 5,251 条；旧路径是种子 2.3 s + 全量扫描约 9 s。

**大库的成员检查。** 大库不跑 `is_stale`（5 万条约 63 s），但打开记忆窗口时
现在会做一次 `SELECT memory_id` + 集合比对（约几十毫秒）：图里没有的、有词法码的
记忆会以「另有 N 条新记忆不在图里」出现在提示里。它只比成员、不比内容，所以
`stale` 仍然是 `None`（没比对内容），不是 `False`——不替没验过的图打包票。

**真 50k 图验证。** 默认 `GraphConfig` 建图：50,000 节点、400,000 条边、170.7 s。
20 条 substrate 查询、`graph_weight` 0.25 与 1.0 下，截断 5,000 与不截断（全量
50,000）的 hit@1 / hit@8 / MRR 以及 top-1 / top-8 注入序列**完全一致**；截断扫描
5,640 条、419/581 ms，不截断扫描 50,000 条、2,184/2,647 ms。截断在这份语料上没有
质量代价。

**界面：局部邻居列表。** 选中一条记忆，下面一栏列出建图那一刻它的前 8 个邻居（按边权
降序），点一条跳过去。**不做全局星图、不引 networkx / matplotlib / QGraphicsView**——
仓里只有 QPainter 自绘的先例，而列表能落在纯层（`memory/browse.py` 的
`association_header` / `neighbor_label`），核心腿就能测。三处判断值得单独记：

* **指向已删除节点的边不静默过滤。** `GraphIndex.neighbors()` 有个 `live=` 参数能把它们
  滤掉，这里**刻意不传**——滤掉之后，"图是旧的、库里删过东西"这件事在界面上完全看不见，
  用户看到的是一份"看起来很正常"的邻居表。改为逐条查一次库，查不到的标「已经不在库里了」、
  不可点，顶栏说出「另有 N 条邻居已被删除，图还没重建」。**图的年纪要说出来，不能靠少显示
  几行来掩盖。**
* **`stale` 是三态，不是布尔。** `True` 确定过期、`False` 刚比对过是最新的、`None`
  **没比对过**（库太大，见下）。`None` 与 `False` 都是假值，但一个说"查过了"、一个说
  "根本没查"，把后者当 `True`/`False` 显示都等于替一份没验过的图打包票。
* **没有数据的地方一个数字都不许出现。** 没图 / 这条不在图里 / 一条邻居都没有，三种
  顶栏文案里连 `0` 都没有——`0 个邻居` 会被读成"算过了、结果是零"，而真实原因可能只是
  边权没过门槛。有数据时才写真数字（边权、记忆权重）。

**建图时机：小库自动 + 大库手动。** 图只在**打开记忆窗口**时自动建（程序启动时无条件建
的话，用不上这个功能的人每次开程序都要等），阈值 `AUTO_GRAPH_MAX = 2000`——按
`graph.py` 的实测表，n=2000 **含编码**是 3.0 s，n=20000 就是 66 s，所以 2000 是"一次全量
重建仍是几秒量级"的最大点（中间档没实测，是外推的）。库比它大时 `GraphWorker` **不遍历、
也不判过期**：`list(iter_items())` 在 5 万条上很占内存，而 `is_stale` 本身是一次全量重编码
（约 63 s）。大库把图当"可能过期但先用着"，由顶栏那句话如实说出来跟你手动兜底。

设置页「记忆」里那个「重建联想」按钮因此**不是可有可无的**：它是大库唯一的兜底。它和自动
那条路共用一个 worker，用 `force` 分开——**手动那条必须真的重建**。少了这个分叉，大库上
点它会原样把旧图还回来（自动那条路的短路条件恰好成立），按钮看起来坏了，还没有任何报错。
同一时刻只跑一趟：两趟会同时写同一个 `graph.npz`，而"哪一趟先落盘"决定盘上最后是哪张图。

> **已知代价**：5 万条手动重建约 4.5 分钟（建图 259 s + 编码 63 s，那是两者之和），而关窗
> 时收尾会等到超时、打印「收尾超时」再放行。**那不是 bug**：建图线程不写库，最坏是白算
> 一次。本版**不做取消**（登记在 [operations.md](operations.md) 的「排障」最后两行里，没有排给哪个阶段）。

> **这一版有四件事只有人眼能验，测试替不了**（跑一次 `run.bat`，开记忆窗口）：邻居行的
> 排版挤不挤（一到两行之间是设计，三行就是坏了）；大库重建时按钮长时间禁用（几分钟）的
> 观感——它是不是看起来像卡死了；`#memoryNeighbors` 与左边那个条目列表放一起协不协调；
> 以及**在真实库上打开开关之后，`min_score`（0.10）是不是明显松了**——最后这条是
> `_GRAPH_CHANNEL_WEIGHT` 需要标定的直接原因，合成语料答不了它。

**P4b 这一版没做的**（越界就登记，不顺手实现）：按通道组合重标 `min_score`（同属那轮还没
排号的标定）、图 A 的增量更新。这一版当时列的另外三项——SNN 热度面板、W 基质、吸引子
回放——**都已在 P4c 落地**（见下一节），所以从这个清单里去掉，而不是留在原地说"还没做"。
`memory/browse.py` 的 `PROBE_CONFIG` 保持 `graph_weight=0`——探针回答的是"以这条为线索
附近还有谁"，联想浏览走邻居面板那条路。

## 睡眠巩固（P4c）

**它的形状由 P4a 那个负数决定。** 全局 W 一步补全在 n=200 上是 0.8700、n=500 上就塌到
0.2250，所以回放**不是**"全库一个 W 取 top-1"，而是**先按关联图分簇、再在每一簇自己的 W
上问"还认不认得自己"**——容量的作用域从全库缩到簇内。簇上限 `MAX_CLUSTER = 200` 取的是
那条曲线上**唯一还活着的实测点**，不是经典 Hopfield 的 `0.138·N ≈ 570`（本仓的相关码把
悬崖提前了）。

一轮做三件事，**次序本身就是要紧的东西**：

1. **分簇**（`memcore/consolidation.py` 的 `partition`，纯函数）：图的 `edges()` 折成无向
   （同一对边取 `max`，与 `diffuse` 同口径）→ 确定性标签传播 → **对超过上限的组做区域生长
   切分**。第二步不是兜底而是主路径：真实库的最短路 top-m 图几乎必然是一整个巨大分量。
   **全程无随机数**，簇序与簇内序都是规范的——`--replay` 的逐条比对靠它。
2. **回放**：每簇现算**簇内文档频率的 `idf` 档**关联码、建一份只装这一簇的 W，对每条做
   50% 丢位探针 + 一步补全。判据是**回放辨认率**，与基质量具的 `completion_top1`
   **同口径**——丢位算子 `drop_bits` 从 `bench/substrate.py` 搬进了 `memcore/sdr.py`，理由
   与 `diffuse` 那次一字不差：**让量具与生产用同一个算子**。`weight` 档保留为 A/B 与
   历史事件回放档（`sleep_once --code-mode weight`）。
3. **改库只做一件事**：`decision == "reinforce"` 的条目 `reinforce_count += 1`（批量一条
   `executemany`）。**不动 `weight`、不更新 `last_access_ts`、不做全库衰减结算**——那三件
   各有各的主人，而 `reinforce_count` 与 `access_count` 分开记，是**独立证据字段**、不是
   权重的输入。v1 也**不做 tier 升降**：那要真实库上的分布作依据，拍一个常量批改全库的
   tier 正是本仓最警惕的"看起来正常的错"。

2026-10-14 起这一趟**多了一件只增不改的事**：把同一会话里时间挨着的碎条目并成一条派生条目（新的一行，原句一字不动，见下文「归并两层」）。上面那句「只改一个字段」说的仍然是**回放**这一趟；归并是并行的另一趟，它只调 store.add。

**事件是每轮一个 JSONL**（`memory/consolidation/<run_id>.jsonl`），一行一条、每行自足、带
`run_seed` 与 `seq`，**`mem.db` 的 schema 一个字节都没改**——事件不是查询对象，是**证据**。
`tools/sleep_once.py --replay <run_id>` 拿同一个 `run_seed` 在同一个库上重跑并**逐条比对**
（`memory_id` / `decision` / `confused_with` / `epoch` 同序相等，`jaccard` 容 `1e-6`，
`at` 不比）。**码档也按事件里记的走**：新事件在 `detail.code_mode` 里写下 `idf` /
`weight`，旧事件没有这个字段就当 `weight`——那是它们当时用的档。换成 idf 默认档之后，
历史轮仍能用原来的档重跑，`--replay` 不会因为默认值变了而报一串假的不一致。
**只比回放决策**：事件文件里还有真跑那一路在回放之后追加的 `merge` / `promote` /
`demote` 行，`consolidate` 不产生它们；拿它们比对会让任何一轮有归并或升降层的巩固都
报"记录里有、重跑没跑出来"（2026-10-18 在 166 条真库上第一次跑真轮时撞到过）。找不到
那个 `run_id` 退 **2**，能重跑但序列不一致退 **3**——一轮巩固不可复现就推翻了这套设计
的全部卖点。事件文件**不轮转**（体积小、是证据），只有快照轮转，这个不对称是刻意的。

**改库之前先拍一份整库快照**（`memory/snapshots/mem-<UTC>.db`，留最近 5 份；按**文件名**
排序轮转而不是 mtime——从备份里拷回来之后每份的 mtime 都是"刚才"，按它排序等于随机删）。
用 SQLite 的**在线备份 API** 而不是 `shutil.copy`：库是 WAL 模式，裸拷 `mem.db` 会漏掉
`-wal` 里未检查点的提交，而漏掉的那部分恰好是**刚刚写进去的记忆**。**空转的一轮不拍**
（一条都没加固，那次修改根本不存在），快照失败就**不改库**——宁可不巩固，也不要一次没
退路的批量改。

**它自己会跑。** `ui/consolidation_scheduler.py` 是一个单发 `QTimer`（**没有抄
`ReminderScheduler` 那个 60 秒上限**：那是为"机器休眠、每 60 秒对一次表"设计的，巩固是
24 小时级的任务，睡晚了只是跑得晚），周期**默认每天一次、默认开**；跨重启的"上次跑过
没有"记在 `memory/consolidation/last.json` 里（它**不是证据**，是给下一次跑用的记录——
坏了只当"不知道"，不算事故，更不会编一个时刻出来）。自动那条路有三道让行，每次都要**先把
表接上**再返回：**已经在跑**（单飞——两轮会重复计数，而且同一个 `at` 秒里起的第二趟会撞上
同一个事件文件名）、**正在生成或装配**（推迟一分钟；这是"用户正忙"的**代理**，不是真
idle 检测，挡不住"用户在别处用这个库"）、**库里的图还没建**（挂起并请一趟建图——图是懒建
的，所以"从没打开过记忆窗口"的人反而是这条路的常客）。

**手动那条路随时可用**：托盘菜单的「立即巩固」，以及设置页「记忆」里那个同名的按钮。它与
自动那条**共用一个 worker、一道单飞守卫、一段收尾**，差别只有两条：**跳过"库里没有新
记忆"那道门**（用户点它就是要跑一趟），以及**回来说不说气泡**——手动弹，自动不弹（否则
每次开机弹一次就是噪音）。反过来，手动也**不排队、不推迟**：已经在跑或正在生成时只回一句
"为什么按不动"。一个按下去没反应的按钮，用户的结论是"它坏了"，然后他会再按一次。

> **登记：自动那趟从此在人前完全无声。** 它跑完之后只有两个落点——记忆界面那句「SNN
> 热度」，以及设置页「记忆」里的状态行；**记忆窗口没开着的时候，一个痕迹也没有**。这是
> 有意的：原来那行会往对话区正中间插一句"认出 4 条 ……（辨认率 28.6%）"，而它每一轮都插。
> 代价是"它到底跑没跑"从一个看得见的事实变成了一个要主动去看的问题——所以手动那趟保留
> 托盘气泡（那是用户自己按的，弹一下不算噪音），而自动那趟不弹（弹了就变成每天一次）。
> 若日后觉得太静，最省事的落点还是托盘，但要有心理准备那就是一天一次的通知。
>
> **失败那趟照旧在对话区说。** 这条不对称是有意的：成功是日常，沉默；失败是"本该发生
> 而没发生"，那正是必须说出口的一类。所以 `_on_consolidation_failed` 一个字没动。

> **这是本版唯一一处"无人值守的批量改库"，三道保险都要说清**：① 快照在最前；② 每簇是一次
> 「改库 + 追加事件」，崩在中途留下的是 `seq` 连续的前缀；③ WAL 保证每个 `UPDATE` 要么整体
> 落盘要么整体回滚，不会留下半截事务。**关窗不会打断它**（本仓关窗只隐藏不退出），只有托盘
> 退出 / Ctrl+Q 才走 `_shutdown`，那时 `wait_for_all` 等 3 秒，超时就打印「收尾超时」放行。
> **第一次看到那行字会吓一跳，它不是 bug。** 本版**不做取消与进度**，与 `GraphWorker` 同一
> 姿态。

**50k 成本实测（2026-10-26）。** 在 substrate 放大语料上跑生产默认的 `idf` 单趟：
建图 **193.6 s**、`partition` 2.5 s、`consolidate` **12.7 s**（731 簇，最大 200，
中位 21，回放 46,374 条）。**巩固本身不是长任务，建图才是。** 所以“每轮全量回放”
不是当前瓶颈；真正的问题是建图之后新增的记忆不在图里，这一轮根本不会参与。
（这份语料的辨认率 1.9% 只说明放大语料在 50k 上没有容量，不是真实库的质量结论。）

**缺口有两个方向。** `RunReport.missing_from_store` 是「图里有、库里没有」（删除），
`missing_from_graph` 是「库里有词法码、图里没有」（建图之后新增）。后者这一轮不
参与，`summary_line` 会写「另有 N 条新记忆不在图里」；把两个方向混成一个数，会让
「该不该重建图」得出相反答案。

**它认得出来多少，量在纸上。** `tools/bench_consolidation.py` 读**同一份**基质语料
（不新造语料、不新冻 `freeze`），把「全局 W(hash) / 全局 W(weight) / 分簇局部
W(weight) / 分簇局部 W(idf)」四列并排报出来：

| n | 全局 hash | 全局 weight | 分簇 weight | 分簇 idf |
| ---: | ---: | ---: | ---: | ---: |
| 200 | 0.0250 | 0.8700 | 0.9000 | **0.9950** |
| 500 | 0.0050 | 0.2250 | 0.4400 | **0.5840** |
| 1000 | 0.0000 | 0.0900 | 0.1370 | **0.3130** |
| 2000 | 0.0000 | 0.0300 | 0.1020 | **0.1960** |

`idf` 档是 2026-10-18 换上的默认档：它把簇内文档频率当作 ALIF 的稳态适应变量，
压掉跨条目公共位（`memcore/sdr.py::encode_assoc_idf`）。**它在**这份语料上每一档都
高于 `weight`，而且 n=200 上已经接近满分。但这份语料 n≥500 的档是**同簇两条句子
拼接**出来的近重复，认错 J 中位随规模涨到 1.0000（n=2000 时 95.5% 的认错都在 0.9
以上）——**它仍然分不开"容量"与"语料重复度"**。所以这里的结论只有一条：**在同一份
语料上，idf 比 weight 好**；不能外推成真实规模上的容量。

真实库上另有一组直接读数：166 条记忆、2 个簇（163 + 3），`weight` 0.6988 →
`idf` **0.8976**（`sleep_once --dry-run` 的口径是 164 条真回放、2 条 pinned 跳过，
辨认率 **0.9085**）。这是 P4c 换默认档的依据；但 166 条不是 5 万条，标签也只有 2 个簇。
完整读数、限度与它为什么不进门槛写在 `benchmarks/substrate/CORPUS.md` 的
「分簇 + 局部 W」那一节——**不进门槛的理由是"只有默认路径进门槛"，而巩固没有默认
路径**（它不参与召回），`baseline.json` 一个字没动。

> **两条登记在案、没有在这里假装已经裁决的占位**：周期 86400 秒**没有实测依据**（一轮只
> 处理一两个簇，工作量与周期无关，与周期挂钩的只有快照频率和磁盘占用）；`MAX_CLUSTER = 200`
> 取自**合成**语料，真实库上最优的簇规模要拿 `reinforce_count` 的分布回头标定。

> **这一版有三件事只有人眼能验**（跑一次 `run.bat`，要么等它自己到点，要么直接按
> 「立即巩固」）：真库上跑完一轮之后「SNN 热度」那句话**读不读得通**；手动那一次弹的托盘
> 气泡在真实使用里**烦不烦人**（自动那趟不弹也不写对话区，所以这条只对手动那趟有意义）；
> 以及**每天一次这个周期在真实节奏下是偏密还是偏疏**——最后这条正是"86400 是占位、没有
> 实测依据"的直接原因。不点界面也能确认这条路算得
> 通的是 `tools/sleep_once.py --dry-run`（跑完整轮、一个字都不写；**没有图它会明说并退 2**
> ——图是懒建的，打开一次记忆窗口就会建），它列在 [operations.md](operations.md) 的「出问题时先跑哪个脚本」里。

## SNN 热度的数据源（2026-10-18）

**面板要的形状是「每条记忆一个标量」，不是「哪条被激活得最强」。** 所以它不读
P4a 的一步补全 argmax，而是读**关联图 A 上的逐条支撑度**：

```
support_i = Σ_j w_ij²        # i 的 top-m 出边权重的平方和
heat_i    = support_i / max(support)   # 归一化到 [0, 1]
```

- `w_ij` 是图 A 的 Jaccard 边权（`hash` 档关联码），**不是** W 的 `idf` 档；
- 强边比弱边贡献大，孤立节点是 0；全库中位数与最高值一起报；
- 选中一条时显示它的热度、高于多少比例的记忆，以及一条十格横条；
- 图的建立时刻与 `stale` 三态照旧如实写出——**图是缓存，不是实时真值**。

**它不是脉冲活跃度。** 这条面板算的是速率级的关联强度；`SpikeTrain` 只是类型边界，
这里没有网络在发放。面板文案禁止出现"脉冲活跃度"（`tests/test_no_journal_voice.py` 与
`tests/test_memory_view.py` 盯着）。

**没有图就没有热度数字。** 面板会说"还没有关联图"，不拿 0 冒充"算过了"；巩固的
`reinforce_count` / `last.json` 是另一份真实数据，照常显示。算法在
`memcore/graph.py::graph_heat`，5 万条 × top-m=8 上是 400k 个元素，毫秒级。

## 时间、归并与完整记忆（2026-10-14）

用户拿真对话戳出三句话，这一节记的是它们各自的落点：

> 能回想起的记忆少，且记忆没有时间戳，模型无法形成时间观念。
> 我需要无论哪一个对话都要能够使用完整的记忆，同时巩固和召回也需要大幅优化。
> 除了官方的上下文限制之外，我希望不要出现任何其他的预算、额度、上下文限制。

外加两条硬约束：**记忆必须完整且本地**，**已有的记忆不允许被改动**。

### 进上下文的每一行都带时刻

L2 那一行以前只有正文（「· 感冒那位回来了」），现在是「· [2026-10-13 22:41] 感冒那位
回来了」。时间写在方括号里、紧挨正文：模型扫一行就同时拿到「什么时候」和「什么事」，
而「昨天我说了什么」全靠这两样挨在一起。

格式只有一处定义（`memcore/timefmt.py`）：装配与归并两处都要用它，各写一套 `strftime`
就会长出两种时间格式，而模型拿两种长得不一样的时间比先后正是这批要治的病。用**本地
时区**，与 L1 环境行的「当前时间：2026-10-13 星期二 22:41」同族。**没时间就不编时间**：
`created_at <= 0` 时那一行不打方括号——编出来的时间比没有时间更坏，它会被模型当事实读。

归并产物挂的是**区间**（「[2026-10-13 13:02–13:05]」），同一天收成紧凑形状、跨天两边
都写全。记忆行按**时间升序**排成一条时间线，时间不可知的排最后：记 0 会把它排到最前，
而模型会把「没有时间」读成「最早」。

### 时间窗：召回的第四通道

「昨天我说了什么」的检索键不是词面，是**时间**。词法与语义都看不出「昨天」意味着什么，
所以这句注定召不回昨天写的那几条——用户看到的是「她记不住事」。

`memcore/temporal_window.parse_time_window` 把中文时间说法翻成本地时区的半开区间
`[since, until)`：今天／昨天／前天／大前天（可带时段，「昨天晚上」收窄到 18:00–24:00）、
今晚／今早／昨晚／昨夜、X月X日、这周／上周（**周一起算**）、这个月／上个月、最近 N 天。

**认不出就返回 `None`，宁可不认不能认错。** 错的一天会把前天的事说成昨天的，比召不回
更坏。所以不认裸数字日期（`10-13` 可能是比分、区间、编号）、不认模糊量（「最近」「前
几天」「前段时间」没有边界）。绝对时刻由**系统**算——与 N.E.K.O 的 `memory/temporal.py`
同一条边界：那边模型只许给相对偏移，换算成 ISO 是系统的事。

命中窗内的条目走第四条通道 `temporal`（只有 0/1 两档），权重默认**给满**：「昨天」是
范围限定不是形容词，窗内那批按定义该排在窗外的前面；给半截权重会被一条窗外但词面撞车
的记忆压过去。窗外的条目照常打分——窗里一条都没有时不至于召回空手。时间窗命中也不因
缺编码被挡：用户问的是那段时间里有什么，而缺编码会在任何不带时间词的轮次里以
`NO_ENCODING` 冒出来。账本写明用了哪个窗、窗内几条。

**召回只取 id。** `MemoryStore.ids_created_between` 只 `SELECT memory_id`；整行版本
`items_created_between` 留给主动搭话等确实需要正文与 SDR 的调用方。50k 覆盖全库的
宽窗口实测：整行版本 1.18 s，id 版本 0.045 s（26 倍）。窗内条目随后由 `_scan` 按
id 批量取，不会解两次。

### 归并两层（巩固的另一半）

「同一件事的碎条目」以前一句一条（「感冒那位回来了」「还带了杯奶茶」），读起来是散的。
现在它合成**一条带时间的记录**，原话附在后面：

```
· [2026-10-13 13:02–13:05] 感冒那位回来了；还带了杯奶茶。
    ↳ 原话：13:02「感冒那位回来了」；13:05「还带了杯奶茶」
```

**头部是并列，不是合成的因果断言。** 「她回来时带了杯奶茶」是新的因果，合错等于往库里
写一句假话；并列句只说「这几句是这段时间里说的」，那永远是真的。所以**只按时间序把原话
连起来，不改写用词**。

判据是**纯算法的，不调任何模型**（本地的也不调）：同一个会话、时间挨着、要么有共同的
二字组要么有一边是碎句。二字组而不是单字——中文没有词边界，单字重合几乎必然（的/了/我），
拿它当「在说同一件事」会让所有碎条目并成一堆。碎句上限 12 字是量出来的：库里完整的事实句
在 12–20 字（「医保报销材料交到街道服务中心二楼窗口」19 字），碎句在 8 字以内（「还带了
杯奶茶」7 字）。早先取 24，一条 19 字的完整事实句就被当成了碎句，与隔壁一句无关的话并成
了一条——那正是「并错」的形状。

**两层**：

1. **库内派生条目**（巩固落库）：`meta` 里带 `derived` / `derived_from` / `span`，正文
   是「并列句 + 逐字原话」。**只增不改**：新写一行，原句一个字都不动。
2. **注入时临时归并**（视图层）：还没被巩固过的新碎条目在发给模型的那一次当场打包，
   **零写库**——关掉程序，库里的形状完全不变。

两层共用 `memcore/merge.py` 的同一套判据。注入取舍：有整理条目代表的原句**不再单独列**
（它的正文里已经带着逐字原话），模型看到的字一个不少，库里的行也一个不少。

### 只增不改

用户的约束是「已有的记忆不允许被你改动」，而归并天然长着一副要改写的样子。所以：

- 巩固归并**只调 `store.add`（新行）与 `bump_reinforce`**，绝不进 `transform`——那是
  改既有行的唯一入口。
- **不迁移、不加列**：`mem.db` 的 `_SCHEMA_VERSION = 1` 无迁移路径，派生信息全走
  `MemoryItem.meta`（既有自由格式字段，注意 `_MAX_META_BYTES` 有体积上限，**原话一律
  进 `content`**）。
- **跑第二遍不重复造条目**：派生条目带 `derived_from`，规划时照它跳过已并过的组。
- **守卫测试**：巩固前后把既有行的 `(memory_id, content, created_at, kind, tier)` 拍快照
  比对，必须逐条相等，多出来的全是带 `derived` 标记的新行。

「不许改」管的是正文：**记账字段照旧写**（`access_count` / `last_access_ts` / `weight` /
`reinforce_count`）——那是用户拍板的口径，否则权重永远冻在写入那一刻。会改正文的三处
（记忆窗口的编辑／删除、`ForgetMemoryTool`、人设编辑）是用户与模型的既有工具，不在这条
约束里。

### 没有份额了

以前装配有一张分配表（L2=0.25 / L3=0.50 / L5=0.20）与一个 `layer_ceiling()`，另外还有
条数上限（一次 8 条）、估算折扣（usable 再砍 10%）、她开口那一轮自己的输出额度——全是
自设的。用户的要求是「除了官方的上下文限制之外，不要出现任何其他的预算、额度、上下文
限制」，所以它们被一个一个拆掉了。

现在装箱只有**一个**上限：窗口本身。顺序是「不可驱逐（人格锚 + 环境 + 本轮输入 + 工具
声明）→ 记忆 → 近处对话 → 工具结果 → 摘要」，**谁先装谁优先**，前一层花剩多少后一层拿
多少；全部装得下时顺序完全不影响结果，而云端 128k 装下全部记忆与整段对话是常态。装不下
时记忆按得分从低到高丢、旧历史进 L4 摘要，账本如实写「N 条没装下」。

**优先级与旧版相反**（旧注释写着「记忆丢得起、近处对话丢了就真没了」）：记忆被丢掉就是
这一轮真的不知道，丢掉的旧对话还有摘要兜着连续性。

**输出额度分后端**：云端 `max_tokens` 一个字都不传（payload 里干脆不出现这个字段，输出
长度走官方默认）；只有 Ollama 那条链留 `DEFAULT_RESERVE_OUTPUT` 并真的传进去——那是它的
协议怪癖：不传 `num_predict` 时它拿同一个 `num_ctx` 生成，把输入挤掉，而挤掉的是最早的
消息、也就是人格锚的位置。判据收成 `reserve_for()` 一处。

留下的、每条都写清为什么它不是上下文额度：`LoopLimits.max_rounds=4`（防工具死循环的
圈数）、路由器分类探针的 `max_tokens=8`（要的是一个词）、麦克风 30 秒（隐私与设备边界）、
`TokenMeter`（尺子不是限额）、摘要是压缩产物所以有自己的行宽。

**没做完的一件**：估算偏低导致请求超长时，「逐出最旧历史后重试一次」这一支还没实现——
装箱是精确填满的，估算偏差只能由服务端发现，而那要靠匹配各家后端的报错文案。现在是如实
报错，不静默砍。

### 基准与产品是两套口径

`RecallConfig.max_items` 的默认值是 `None`（注入全部），而**基准显式给 8**
（`bench/harness.py` 的 `BENCH_MAX_ITEMS`）。这是刻意的分叉：

* 基准量「挑得准不准」，那要有槽位才谈得上排序质量；而 `false_injection_rate` 的口径在
  槽位填满时会饱和（它自己的 docstring：「主要响应注入了多少条，而不是排得准不准」），
  不给上限就退化成「库里有多少条不是金标准」——那是语料的性质，不是召回的性质，而且会
  撞上 `SANITY_CEILING`（0.9）那道防假基线的门。
* 生产注入全部是产品口径。排序质量在生产里仍然有用：窗口真满时按得分从低到高丢。

实测（纯词法金标准）：`hit@1` / `hit@8` / `MRR` / `AUC` 四项与基线逐位相同，动的只有
误注入率——这正是它被单独关进量具口径的理由。

## 纯词法召回的倒排候选（2026-10-18，2026-10-19 修正候选排序）

**只在没有语义/时间/图通道时启用。** 这些通道的命中可能没有词法重叠，只按词法位
过滤会漏掉它们；所以 `recall` 的判断是：

- `query_vector is None`、`graph_weight <= 0`、`window_ids is None`、且库里**每个
  条目都有词法码** → 用 `MemoryStore.lexical_index()` 的倒排表取候选（上限
  `_PREFILTER_LIMIT = 1000`）；
- 语义/时间/图通道存在时，取各通道候选的并集（词法 + 语义 top-M + 时间窗 + 图
  正分）；并集超过 20,000 或存在无词法码条目时退回全量扫描。

**候选按精确 Jaccard 排序，不按倒排表的出现顺序截断。** 2026-10-19 在 50,000 条
真实文本放大语料、40 条 substrate 查询上实测：旧的"稀有位先 gather、凑满上限就
停"在 5,000 条时只覆盖精确 top-8 的 0.475，hit@1 为 0；改成按
`|A∩B| / |A∪B|` 排序后，取 1,000 条即可达到 hit@1 0.850、hit@8 0.975，并且
500 / 1,000 / 2,000 / 5,000 / 全量 50,000 的指标逐位相同，耗时随候选数线性增长。
排序口径与 `SDR.jaccard` 相同（忽略权重），候选阶段不改变最终融合/MMR 的语义。

索引按 `MemoryStore.revision` 缓存。**新增条目走 delta，不再整库重建**：50,000 条
上首次构建约 3.5 s（静默机器；有重活并行时 22 s），此后前 100 条新增实测
**1.5 ms/条**，delta 接近上限时约 **9.3 ms/条**；delta 满 512 条后下一次
`lexical_index()` 做一次全量合并（约 3.5 s），成本摊到每 512 条。`add` 覆盖既有
id 或 `delete` 仍直接让索引失效——更新/删除是低频动作，不值得维护 tombstone。
索引由 `LexicalIndexWorker` 在主窗口启动时后台预建（库 ≥ 2,000 条才起）。
金标准词法四项逐位不变。没有词法码的条目会让整轮退回全量扫描，保证
`NO_ENCODING` 仍然出现在账本里。
