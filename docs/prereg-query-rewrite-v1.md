# 预注册：查询改写能否抬高硬改写检索（v1，2026-11-02）

**状态：判据先落盘，代码未写。**

## 问题

召回在"不点站名"的硬改写上只有 hit@1 = 0.40（bge 嵌入，见
`benchmarks/recall_embedding_swap.md`）。配置层已扫完、权重已到平台区，
所以下一刀只能动结构：**把提问先改写成接近记忆的说法，再检索**。

## 判据（跑之前写死）

| # | 判据 | 门槛 |
| :--- | :--- | :--- |
| Q1 | `benchmarks/paraphrase_v1_hard/` 20 条上的 hit@1 | **≥ 0.60**（基线 0.40） |
| Q2 | 单次查询的额外延迟 | **< 300 ms** |
| Q3 | 在 gold 全体 85 条上不得倒退 | ≥ 0.909（基线） |

**选择与报告分离**：改写器的任何可调项（提示词版本、是否拼原句、检索条数）
只在 gold 的**验证半**上选；留出半与硬改写集只报数、不选参。

## 怎么搭（跑之前定死）

- 改写器：本地 `qwen3-4b`（Ollama，`temperature=0`，thinking 关闭），
  输入是原提问 + 一条指令，输出一句"接近记忆写法"的问句；
- 检索：改写后的问句与原问句**各检索一次，取并集**（不是只用品改写结果——
  改写可能丢掉原句里的名字）；
- 嵌入：`local/bge-small-zh-v1.5@512`；权重沿用 1.2 / 0.45 / 1.5（已标定）；
- 延迟：只计改写那一次生成的墙钟时间，不含检索；
- 种子：生成温度 0，故改写是确定性的；仍需跑 3 次确认逐字相同。

## 失败长什么样

- 若改写后的问句与原问句高度相同（字面重合），说明模型没在改写、只是复述 →
  记录"改写无效"，不是"检索无效"；
- 若并集让 gold 上的精确类下降（Q3 不过），说明改写引入了噪声候选；
- 若延迟超 300 ms，则这条路线在产品上不可用，无论命中多高。

## 跑之前的预期

改写大概率能抬高命中（它直接对准"字面差距"这个失分来源），但**延迟很可能是
硬约束**：qwen3-4b 在 8GB 显卡上生成一句 20–40 字问句通常要几百毫秒到一秒。
如果 Q2 不过、Q1 过，结论应写成"有效但太慢"，并给出离线/异步改写的替代方案，
而不是悄悄放宽延迟门槛。

---

## 结果（2026-11-02，n=20）

| 指标 | 值 |
| :--- | ---: |
| 基线 hit@1 | 0.300 |
| 改写 + 并集 hit@1 | **0.300** |
| 改写延迟（中位 / 最大） | 171 ms / 284 ms |
| Q1（≥0.60） | **不过** |
| Q2（<300 ms） | 过 |

**改写没有带来任何提升**，原因就写在样本里：qwen3-4b 的输出与原句几乎逐字相同
（"靠海那个浮标站…" → "靠海的那个浮标站…"、"二号站那边电池掉到两成会告警吗？" → 原样返回）。
这不是"检索不行"，是**改写这一步没发生**——预注册里写的三种失败形态，命中的是第一种。

两点必须记下来：

1. **基线口径不同**：本脚本用默认 `RecallConfig`，基线 0.300；`benchmarks/recall_embedding_swap.md`
   里用调优后的权重（1.2/1.5）测得 0.400。两者不可混用，Q1 的门槛 0.60 是相对后者定的，
   这意味着本次的差距被低估了（真实差距更大），结论方向不受影响。
2. **关思考是前提**：第一版没关，模型把 `<think>` 块当正文输出，改写结果等于一段推理前言；
   关掉 `think` 并剥离 think 块之后才有可用的输出。

## 下一步（若继续这条线）

改写器换更强的模型，或改任务形式（不给"改写"这种弱指令，而是"用另一种说法描述这个场景"）。
但在换之前要先回答一个问题：**延迟预算 300 ms 是为在线路径定的**；如果只能离线改写，
那它服务的是索引侧而不是查询侧，问题定义要重写。

## 结果二（2026-11-02，换任务形式后）

把指令从"改写提问"换成"用另一种说法描述场景，不许沿用原句的名词与数字"：

| 指标 | 基线 | 强指令改写+并集 |
| :--- | ---: | ---: |
| hit@1 | 0.300 | **0.150** |
| 改写延迟（中位） | — | 188 ms |
| Q1（≥0.60） | — | **不过（方向为负）** |
| Q2（<300 ms） | — | 过 |

**改写把结果弄坏了，不是没帮上忙。** 样本说明了原因：模型把"两成"改成了"二十 percent"，
把"电池"改成"电池电量"，**主动离开了记忆原文用的词**。对一个靠词法与嵌入混合打分的检索器，
这等于把查询从锚点上拽开——并集里多出来的候选把正确答案挤下了第一位。

两次尝试合起来给出一条结论：在**模板化语料 + 词法通道占主导**的检索器上，查询改写是负向的。
这条结论不推广到"真实用户提问"上——那里词法锚点本来就少，改写的收益可能要另测。
